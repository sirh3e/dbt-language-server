1. Setup                                               *cogitator-nvim-setup*

Requires Neovim 0.11+ and the `cogitator` binary (a release asset or
`cargo build --release -p cogitator`). >lua

    require("cogitator").setup({})
<
With lazy.nvim the plugin is one line; the repository's own lazy.lua
puts editors/nvim on the runtimepath and passes `opts` to setup(): >lua

    { "sirh3e/dbt-language-server", opts = {} }
<
editors/nvim/examples/lazy.lua is a fuller spec: lazy-loading on
BufReadPre of SQL/YAML files (not `ft`, which comes too late for the
server to attach to the first buffer) and an opt-in `build` that installs
the server from the latest release on install and :Lazy update.
editors/nvim/examples/minimal_init.lua tries the plugin without touching
your config: `nvim -u minimal_init.lua some_model.sql`.
The server attaches to `sql` and `yaml` buffers inside a dbt project (a
directory with `dbt_project.yml` upward from the file). Run
`:checkhealth cogitator` to verify the binary, the project root and the
profiles.yml resolution.

                                                *cogitator-nvim-no-server*
Without a server binary nothing can attach. When `cmd` is the default
`cogitator` and it is not on Neovim's PATH, the plugin looks where
install.sh puts it ($COGITATOR_BIN_DIR, then ~/.local/bin). Without
one, the first SQL or YAML file of a dbt project you open says so once,
and |:DbtInstall| installs it and starts it. The keymaps are set on
such buffers either way, so `<leader>d…` never falls through to Vim's
own `d`; a command that needs the server says why there is none (not a
dbt project, no binary, still starting, exited).

2. Options                                           *cogitator-nvim-options*

Defaults shown: >lua

    require("cogitator").setup({
      cmd = { "cogitator" },      -- server command; flags are appended
      profiles_dir = nil,         -- profiles.yml dir → initializationOptions
      fusion = false,             -- true, or "/path/to/dbt" for Fusion mode
      tree_sitter = true,         -- false → --no-tree-sitter
      debug = false,              -- true → --debug (log.txt next to binary)
      filetypes = { "sql", "yaml" },
      root_markers = { "dbt_project.yml" },
      attach_outside_project = false, -- true: fall back to cwd as root
      lens = {
        enabled = true,
        events = { "BufEnter", "CursorHold", "InsertLeave" },
      },
      keymaps = true,             -- the buffer-local <leader>d maps below
      semantic_tokens = true,
      inlay_hints = false,        -- true: relations after ref(), the value
                                  -- of each var() (= 'jaffle'), macro params
      highlight = {               -- |cogitator-nvim-highlight|
        server = "auto",          -- "always" | false: colours from the server
        layers = { yaml = true, sql = true, jinja = true, dbt = true },
      },
      lineage = {                 -- column-lineage graphs (|cogitator-nvim-lineage|)
        depth = 3,                -- hops followed each way
        max_requests = 60,        -- dbt.columnLineage calls per graph, at most
      },
      dag = {                     -- |:DbtDag|
        focus_depth = 2,          -- hops shown around the selection (f, +/-)
        follow = false,           -- start with follow mode on (F)
        refresh_on_save = true,   -- redraw an open DAG after a save
      },
      grammar = {                 -- |cogitator-nvim-treesitter|
        highlight = true,         -- start tree-sitter-dbt on sql buffers
        auto_install = false,     -- build it on first attach when missing
        url = nil,                -- another tree-sitter-dbt repository
        rev = nil,                -- another revision than the server's
      },
      ui = {                      -- |cogitator-nvim-dialogs|
        picker = true,            -- false → the `picker` backend, vim.ui.input
      },
    })
<
`profiles_dir` is sent as `initializationOptions.profilesDir`; the server
resolution order is: this override, `$DBT_PROFILES_DIR`,
`<root>/profiles.yml`, `<root>/.dbt/profiles.yml`, `~/.dbt/profiles.yml`.

3. Commands and keymaps                             *cogitator-nvim-commands*

  :DbtRun        dbt run for the current model       <leader>dr
  :DbtTest       dbt test for the current model      <leader>dt
  :DbtCompile    dbt compile; opens compiled SQL     <leader>dc
  :DbtParse      dbt parse; refreshes the context
  :DbtPreview    dbt show result rows ([limit], default 50)
  :DbtPreviewCte rows of the CTE under the cursor ([limit]) in a split
  :DbtRelation   yank database.schema.identifier     <leader>dR
  :DbtProjects   pick a known dbt project            <leader>dP
  :DbtQuery      bounded SELECT on the relation      <leader>dx
  :DbtCache      derived-cache stats ('clear' empties)
  :DbtSchema     jump to the schema.yml entry        <leader>ds
  :DbtLineage    show column lineage (message)       <leader>dl
  :DbtGraph      model-graph browser                 <leader>dg
  :DbtBrowse     the model explorer                  <leader>db
  :DbtProfiles   show/switch the profiles directory
  :DbtTarget     pick the active profile/target      <leader>dT
  :DbtExtract    model → schema YAML / add version   <leader>dy
  :DbtTests      jump to a test of this model        <leader>dq
  :DbtStatus     language-server status              <leader>dS
  :DbtDag        project DAG, dbt-docs style         <leader>dD
  :DbtTags       pick a tag, then a model
  :DbtSelectors  pick a selectors.yml entry
  :DbtFind [src] fuzzy-find: models, sources, all,       <leader>dF
                 definitions, macros, columns, upstream,
                 downstream, lineage, refs, tests, tags,
                 selectors, astgrep (models <leader>df, definitions
                 <leader>dd, columns <leader>dk, upstream
                 <leader>du, downstream <leader>dU)
  :DbtPlan       IR levels, findings, incrementality
  :DbtSplit      split a table model at its incrementality frontier:
                 the plan as an S-expression and the new model's file;
                 `a` applies the split, `q` closes
  :DbtIncrementalDiff
                 this model rendered with is_incremental() false and
                 true, as a unified diff in a split (`q` closes)
  :DbtIncrementality
                 table models that could be incremental (quickfix)
  :DbtBreakingChanges
                 this model against its last built schema (target/
                 catalog.json, else manifest.json): removed, possibly
                 renamed and retyped columns and what reads them
                 downstream (quickfix); also a lens and a diagnostic,
                 refreshed on save
  :DbtUnresolved [kind…]
                 every unresolved ref, source, source_table, doc, macro
                 and var of the project (quickfix; `:DbtFind unresolved`
                 is the same list in the picker)
  :DbtSelect {selector}
                 the nodes a dbt selector picks, as `dbt ls` lists
                 them (`selector:<name>` evaluates a selectors.yml
                 entry), into quickfix; `:DbtFind select` is the same
                 list in the picker
  :DbtColumnLineage [column]  column-lineage graph of this model
  :DbtDeps       dbt deps for the project (cancellable)
  :DbtInstall    install or update the language server from this
                 repository's releases (checksum-verified install.sh),
                 then start it; the plugin also finds a server in
                 $COGITATOR_BIN_DIR or ~/.local/bin when it is not on
                 PATH
  :DbtReloadConfig  re-read cogitator.yml now
  :DbtSyntaxTree the tree-sitter-dbt tree in a split (toggle)
  :DbtHighlight[!] [auto|always|off]
                 colour this buffer from the server (toggle); ! sets
                 when buffers are coloured on open
  :DbtNode [kind:]name  a node's card: macro, test, source… (dbt.nodeInfo)
  :DbtAstGrep [sql:]pattern [=> rewrite]                <leader>da
                 ast-grep: matches to quickfix; a rewrite after asking
  :DbtTreesitter [install|status|start]  the grammar in Neovim
  :DbtProjects!  manage a known project (profiles, rename, forget)
  (code lens)    run the code lens on this line      <leader>dL
  (selection)    expand along selectionRange         <leader>dv
  :DbtActions    code actions, yazi-style menu       <leader>dA, gra
                 shrink back (visual mode)           <leader>dV

Every command is also a subcommand of *:Dbt* with completion, e.g.
`:Dbt columns customer_id`, `:Dbt cache clear`, `:Dbt treesitter install`;
`:Dbt` alone lists them.

`:DbtDag` (a Neovim-only feature) draws the whole project as a layered
DAG in the dbt-docs colours. One node is selected, and movement goes
from node to node:

  h / l          a connected parent / child (nearest by row, or back the
                 way you came)
  j / k          next / previous node in the same layer
  gg / G         first / last node ([count] goes to that node)
  { / }          first / last layer ([count] counts from that end)
  /              search node names live; n / N step through the matches
  <C-o> / <C-i>  older / newer selection
  <CR>           open the selected model
  c / C          expand columns in this / every node (docglow-style)
  L              column-lineage graph of this model; on an expanded
                 column line, of that column; in a column graph,
                 re-centre on the column under the cursor
  m              back from a column graph to the model graph
  f              focus: only the selection's neighbourhood, or all again
  + / -          widen / narrow the focus (in a column graph: the walk)
  F              follow: select the model of the buffer entered elsewhere
  R              refresh (a save does it too, see `dag.refresh_on_save`)
  q              close

The winbar says what is shown: the models, a focus and its depth, or
the column graph and its origin.

                                                     *cogitator-nvim-lineage*
A column-lineage graph is walked from `dbt.columnLineage`, which answers
one model at a time: upstream through the model and source columns each
column reads, downstream through the models that read it, up to
`lineage.depth` hops and `lineage.max_requests` requests (the winbar
says when the walk stopped early). A column of a model whose template the
server declines (Jinja control flow) has no lineage; compiling it
(|:DbtCompile|) lets the server read the compiled SQL instead.

Counts repeat h, j, k, l, n, N, <C-o> and <C-i>. The colours are the
`DbtDag*` highlight groups, which a colorscheme can override. Search
also works through |vim.lsp.buf.workspace_symbol| with `tag:x` and
`selector:x` queries.

Nothing waits on the server: every request is asynchronous. `<leader>dv`
selects when the server's answer arrives (and not if you moved on), column
completion for :Dbt impact / :DbtColumnLineage answers from the columns
fetched in the background, :checkhealth shows the dbt.doctor report
fetched at attach and after each refresh, and a large :DbtDag is coloured
in slices while you keep working.

PICKERS                                                   *cogitator-pickers*

:DbtFind shows its list in your picker: fzf-lua, snacks.picker or
telescope when one is installed (setup `picker = "auto"`, in that order),
or the one you name (`picker = "fzf-lua" | "snacks" | "telescope" |
"builtin"`). Without one, the built-in picker: a prompt, the ranked list
with the matched letters highlighted and a preview. The query is fzf's:
`fzy` fuzzy, `'exact`, `^prefix`, `suffix$`, `!not`, `a | b`, words AND.

  <CR>            open              <C-v> <C-x> <C-t>   vsplit split tab
  <C-g>           the navigator     <C-y>               yank the names
  <C-r>           dbt run them      <Tab>               mark
  <C-j> <C-k>     move (built-in)   <C-d> <C-u>         scroll the preview

Every other choice (:Dbt, :DbtTests, :DbtTags, :DbtCancel, targets,
projects) uses the same picker.

EXPLORER                                                 *cogitator-navigator*

:DbtBrowse (<leader>db) shows one model, opening on the buffer's model:

    upstream ⯇       |   the model's card   |   ⯈ downstream
    dbt SQL                  |                 compiled SQL

The card holds the description, tags, relation, versions, columns and
tests (<CR> on a test or a version opens it). h/l enter the side panes
and, pressed again there, walk the lineage; <CR> on an entry makes it
the model. [ or - goes back, ] forward, and the card's title is the trail
walked. f or / picks any model with the fuzzy picker; . lets it take
every kind of node. p enters the dbt SQL, h/l move between the SQL
panes, <Esc> returns, J/K scroll both. <Space> marks, y yanks and r
dbt-runs the marked; o s v t open, c compiles, g :DbtDag, L column
lineage; ? lists the keys.

Context refreshes and dbt runs also report through $/progress, so they
appear in |vim.lsp.status()| and plugins like fidget.nvim.

A `cogitator.yml` at the project root configures the server and is
hot-reloaded on save (see the server README's "Configuration file");
`:DbtStatus` shows whether one is loaded and any parse error.

The server logs what it is doing to |vim.lsp.log| (`:LspLog`): context
refreshes and warnings at the default info level; set
`log.client_level: debug` in cogitator.yml (hot) or send `$/setTrace`
for per-request timing lines.

`:DbtProfiles` without an argument prints the server's profiles.yml
resolution order with the winning candidate marked. With a directory
argument it switches the directory LIVE through `dbt.setProfilesDir`
(no restart) and remembers the choice for this project in the manager
store; against older servers without that command it falls back to the
restart flow. `:DbtTarget` choices persist per project the same way,
and `:DbtProjects` picks among every project the store knows;
`:DbtProjects!` manages one: open it, set or clear its profiles
directory and profile/target selections, give it a name, or forget it. The
store is a JSON file at `stdpath("data")/cogitator/manager.json`
(override with setup's `manager_path`); stored selections are injected
as initializationOptions on the next attach.

The graph browser (|:DbtGraph|) is a yazi-style three-pane float: direct
upstream models on the left, the current model in the center, direct
downstream models on the right. Keys inside it:

  h / l          from the center: enter the upstream / downstream pane
                 in a side pane: h upstream or l downstream walks one
                 step further along the lineage ([count] walks that
                 many); the opposite key returns to the center
  j / k          select an entry in a side pane
  <CR>           re-center the graph on the selected neighbor
  o              open the selected entry's file (center: the model itself)
  y              yank the selected entry's name
  q / <Esc>      close the browser

Sources appear in the upstream pane tagged `[source]`; they have no
further lineage behind them.

`:DbtBrowse` (a Neovim-only feature) is the project-wide browser:
the center pane lists every model, the side panes follow the selection
with its direct upstream and downstream, and the preview below shows
the selected model in four tabs. Keys inside it:

  j / k          select a model (the panes follow, debounced); counts
                 and the other native motions work (5j, gg, G, <C-d>)
  n / N          step through the list, wrapping at the ends
  /              filter the list live (smart-case substring);
                 <BS> edits, <CR> accepts, <Esc> clears
  h / l          from the center: enter the upstream / downstream pane
                 in a side pane: h upstream or l downstream re-centers
                 on the entry and stays, so pressing it again walks the
                 lineage ([count] walks that many); the opposite key
                 returns to the center
  p              focus the preview pane (h returns)
  J / K          scroll the preview from any pane
  <Tab>          cycle the preview tabs (<S-Tab> reverses)
  [count]<Tab>   preview tab [count]
  <CR>           side pane: re-select that model in the center
                 center: open the model file and close
  o              open the selected entry's file
  y              yank the selected model's or entry's name
  s / v / t      open the selected entry in a split / vsplit / tab
  c              compile the selected model (the compiled SQL opens)
  g              show the selection in |:DbtDag|
  L              the selection's column-lineage graph
  P              dbt parse for the project
  <Esc>          clear the filter first, close second
  q              close the browser

The preview has four tabs (1 raw / 2 compiled / 3 versions+tests /
4 info — description, tags, relation name, documented columns, and
tests whose <CR> jumps to their YAML entry). `:DbtExplorer` is an
alias of |:DbtBrowse|.

The compiled tab fetches `dbt.compiledSql` from the server (which reads
`target/compiled/<project>/…`) and never runs dbt — when nothing is
there it shows a hint to run |:DbtCompile| instead.

Code lenses on each model: "N downstream", "N upstream", "Go to schema",
"Column lineage", "dbt run", "dbt test", "dbt compile"; macros get an
informational "N call sites" lens (not executable).

The same command set is served as code actions
(|vim.lsp.buf.code_action|): on a `ref('x')` an "Open schema of 'x'"
action is added, and inside a schema YAML the model entry under the
cursor offers "Open model" and "Go to tests".

                                                *cogitator-nvim-code-actions*
`:DbtActions` (<leader>dA, and `gra` in dbt buffers; also on a visual
selection) opens every action at the cursor in one menu. What is about
the cursor comes first, each chosen with one key (<CR> or `l`): a fix
of the diagnostic there (a preferred one starred), then the refactors
and commands of what is under it — "Expand * to 18 column(s)" on a
`select *`, "Extract CTE 'x' to a model" on a CTE's name, "Open schema
of 'x'" on a `ref('x')`. The server says which actions those are (in
the action's `data`). Below them "This model · <name>" holds the
server's actions on the whole file (dbt run, Go to schema, Add version
2…) beside the plugin's own model commands (the plan, the split,
preview, impact…); with nothing at the cursor these are the top level
themselves. Then Views, Project and Session: the plugin's commands,
which the server cannot offer itself, since a stock client drops what
they answer. A server command the plugin also has (dbt run, Go to
schema) is listed once. The preview column shows what an action does:
an edit as a diff of every file it touches (and the files it creates or
renames), a command with what it runs. With `ui.picker = false` the
keymaps fall back to |vim.lsp.buf.code_action|.

                                                      *cogitator-nvim-dialogs*
Every dialog of the plugin — the code actions, `:Dbt` without
arguments, target and project pickers, tests, tags, selectors, jobs —
is a yazi-style float: the parent level on the left, the current level
in the middle, a preview of what is under the cursor on the right, the
path above and the keys below. Prompts (a selector, a directory) are a
one-line float with a title.

  j  k          move (counts work: 3j); wraps at the ends
  l  <CR>       enter a group, or choose the item
  h  <BS>       back to the parent level
  gg  G         first / last item
  <C-d>  <C-u>  half a page down / up
  J  K          scroll the preview
  /             filter as you type; a group stays while a child matches,
                and the filter follows you into it (<Esc> clears it)
  ?             the keys, in the preview column
  q  <Esc>      close

In a prompt: <CR> accepts, <Esc> goes to normal mode and <Esc> or q
cancels, <Tab> completes a directory. `ui.picker = false` sends the
choices to the `picker` backend instead (fzf-lua, snacks.picker,
telescope or the built-in one) and the prompts to |vim.ui.input|. The
fuzzy finders (|:DbtFind|, tests, tags, selectors) always use that
backend.
The colours are `DbtPicker*` groups linked to the colorscheme's.

dbt run/test/compile are asynchronous; progress and results arrive as
notifications (`:messages` keeps them).

                                                      *cogitator-nvim-syntax*
`:DbtSyntaxTree` opens the server's tree-sitter-dbt tree of the buffer
(`dbt.syntaxTree`) in a split, one node per line with its field and
range; ERROR and MISSING nodes are highlighted. The tree's cursor
follows the source cursor to the innermost node, moving in the tree
highlights that node's range in the source, <CR> jumps there, q closes.
Edits refresh it after a short pause.

                                                  *cogitator-nvim-highlight*
The server colours dbt files with grammars that know dbt (`dbt.highlight`):
models, macros and tests by tree-sitter-dbt (the Jinja) and the SQL grammar
it injects; compiled SQL as SQL; YAML by tree-sitter-yaml, with the Jinja
and the SQL inside its values and dbt's meaning — model, source, column,
test, macro and doc names, config keys, `ref()`s (`.unresolved` when the
project lacks them). Captures become Neovim's tree-sitter groups
(`@keyword`, `@type.dbt.model` → `@type`, `@property.dbt.column`), so your
colourscheme applies; nothing needs to be installed in Neovim.

`highlight.server` (setup) says when: "auto" (default) colours SQL buffers
Neovim's own tree-sitter does not, and every YAML file of the project (the
yaml layer left to Neovim's yaml highlighter when it runs); "always" every
buffer; false only on `:DbtHighlight`. `highlight.layers` turns a layer
(yaml, sql, jinja, dbt) off. Colours follow edits after a short pause.
`:DbtHighlight` toggles the current buffer; `:DbtHighlight! {mode}` sets
the mode for the session. The explorer's SQL panes and picker previews are
coloured the same way. See docs/highlighting.md.

                                                       *cogitator-nvim-node*
`:DbtNode [kind:]name` shows a node's card in a float (`dbt.nodeInfo`): a
macro's signature, callers and calls; a test's refs; a generic test's
places in YAML; a model's neighbours. Without a kind the kinds are tried
in order. <CR> opens the line's target, q closes.

                                                    *cogitator-nvim-astgrep*
`:DbtAstGrep {{ ref($M) }}` searches the project's dbt files with ast-grep
over tree-sitter-dbt (`dbt.astGrep`) and fills the quickfix list; `$M` is
a metavariable, `$$$A` several. The SQL between the tags is text to the
dbt grammar, so a dbt pattern matches Jinja; prefix `sql:` for a whole SQL
statement over the compiled SQL (`sql:select $$$C from $T`). With
`pattern => rewrite` the matches are listed and, after asking, rewritten
(`{{ ref($M) }} => {{ ref('core', $M) }}`). `:DbtFind astgrep`
(`<leader>da`) asks for a pattern and shows the matches in the picker.
The project's `sgconfig.yml` rules show as diagnostics with their fixes as
code actions — see docs/ast-grep.md.

                                                  *cogitator-nvim-treesitter*
`:DbtTreesitter install` builds the tree-sitter-dbt grammar at the
revision the server is built with (git, and $CC, cc or `zig cc`) and
installs it with its queries into `stdpath("data")/site`. With
`grammar.highlight` on, the plugin then starts it on every `sql` buffer
it attaches to: the filetype stays `sql`, so other SQL tools keep
working, while highlighting sees the Jinja; the SQL between the tags is
injected as `sql`, highlighted when a SQL parser is installed.
`:DbtTreesitter` (or `status`) says what is installed, and
|:checkhealth| warns when it is behind the server's revision.

                                                   *cogitator-nvim-select*
<leader>dv selects the innermost `textDocument/selectionRange` around
the cursor and, pressed again in visual mode, the next larger one
(expression, Jinja block, CTE, statement, document); <leader>dV shrinks
back the way it came. Or call `require("cogitator.select").expand()` /
`.shrink()` from your own maps.

                                                      *cogitator-nvim-cmp*
For nvim-cmp, `cogitator.completion` orders cogitator's items by the
server's sortText and shows an item's detail in the menu: >lua

    local dbt = require("cogitator.completion")
    cmp.setup({
      sorting = { comparators = dbt.sorted(cmp.config.compare) },
      formatting = { format = dbt.format() }, -- or dbt.format(lspkind_fn)
    })
<
|:checkhealth| cogitator also lists every command and method the plugin
uses that the attached server does not offer, and what stops working.

==============================================================================
4. Caveats                                           *cogitator-nvim-caveats*

- Rename (|vim.lsp.buf.rename()| on a model or `ref`) rewrites dependents,
  the schema.yml entry, and renames the model file. Dependents are read
  from disk: save other modified buffers before renaming.
- Completion ranking comes from the server via `sortText`; keep your
  completion engine's sortText comparator enabled.

5. Neovim 0.10 fallback                                 *cogitator-nvim-0.10*

Without |vim.lsp.config()|, configure through nvim-lspconfig: >lua

    require("lspconfig.configs").cogitator = {
      default_config = {
        cmd = { "cogitator" },
        filetypes = { "sql", "yaml" },
        root_dir = require("lspconfig.util").root_pattern("dbt_project.yml"),
        init_options = { profilesDir = nil },
      },
    }
    require("lspconfig").cogitator.setup({
      capabilities = vim.tbl_deep_extend("force",
        vim.lsp.protocol.make_client_capabilities(), {
          window = { showDocument = { support = true } },
          workspace = { workspaceEdit = {
            documentChanges = true,
            resourceOperations = { "rename" },
          } },
        }),
    })
<
vim:tw=78:ts=8:ft=help:norl:
